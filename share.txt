**Authentication flow details (exact app expectations)**
- Login: POST /api/auth/login returns { token, user }. The app stores `token` in SharedPreferences and uses it in `Authorization: Bearer <token>` for subsequent requests.
- Register: POST /api/auth/register returns { token, user } and app stores token similarly.
- Token validation: GET /api/me must return { status:'success', user: { ... } } — the app expects `data['user']` in `ApiService.getCurrentUser()` and constructs the local `UserModel` from that user object.
- Role enforcement:
  - `student` role: allowed to GET /api/buses, /api/schedules, /api/notifications but restricted to own `hostelId`.
  - `caretaker` and `admin`: allowed to create/update buses, schedules, send notifications, modify drivers.

**Hardware / ESP32 guidance for teammate**
- Provide a server key config: `API_SECRET_KEY` (same value used by ESP32 firmware).
- Expose secure endpoint POST /api/update-location that requires header `x-api-key` and accepts JSON described above.
- The endpoint should insert the telemetry row and update the `buses` table when bus ID numeric value is identified (server-side convenience).
